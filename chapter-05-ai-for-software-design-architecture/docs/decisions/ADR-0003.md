# Quyết định Kiến trúc: ADR-0003 — Chiến lược Cô lập Dữ liệu Đa thuê bao (Multi-tenant Isolation) trên MySQL 8.0

- **Trạng thái**: ĐÃ PHÊ DUYỆT (ACCEPTED)
- **Ngày quyết định**: 2026-11-16
- **Người quyết định**: Trưởng bộ phận Kiến trúc Phần mềm & Kỹ sư CSDL chính
- **Phạm vi tác động**: Sơ đồ Cơ sở dữ liệu MySQL 8.0, cấu hình Prisma ORM, và toàn bộ truy vấn dữ liệu.

---

## 1. Ngữ cảnh & Vấn đề (Context)

ReplyMind là nền tảng SaaS phục vụ đồng thời hàng trăm thương hiệu D2C độc lập (ví dụ: Lumina Fashion, ZenWear, GreenCosmetics,...).
Dữ liệu của mỗi thương hiệu — bao gồm hội thoại khách hàng, thông tin đơn hàng, bài viết chính sách nội bộ và cấu hình văn phong kinh doanh — là tài sản bảo mật tối cao. Hệ thống phải đảm bảo:
- **Tuyệt đối không rò rỉ dữ liệu chéo (Cross-tenant Data Leakage)**: Nhân viên thương hiệu A không bao giờ có thể truy cập hoặc nhìn thấy dữ liệu của thương hiệu B.
- **Tối ưu chi phí hạ tầng**: Phù hợp với mô hình kinh doanh SaaS giai đoạn tăng trưởng (10 đến 500+ thương hiệu).
- **Hiệu năng truy vấn cao**: Tốc độ tìm kiếm hộp thư và lấy ngữ cảnh RAG dưới 100ms.

---

## 2. Các Lựa chọn Đã Cân nhắc (Options Evaluated)

### Lựa chọn A: Database-per-Tenant (Mỗi thương hiệu 1 CSDL MySQL riêng)
- **Ưu điểm**: Mức độ cô lập vật lý cao nhất; việc backup/restore cho từng thương hiệu hoàn toàn độc lập.
- **Nhược điểm**: Chi phí vận hành đắt đỏ; việc chạy Database Migrations cho hàng trăm database tốn nhiều thời gian và dễ lỗi; connection pooling phức tạp, quá tải tài nguyên máy chủ.

### Lựa chọn B: Schema-per-Tenant (Mỗi thương hiệu 1 MySQL Schema/Database trong cùng 1 cụm máy chủ)
- **Ưu điểm**: Cách ly logic ở mức schema.
- **Nhược điểm**: MySQL xử lý schema tương đương với database; vẫn gặp phải giới hạn tài nguyên kết nối và migration phức tạp.

### Lựa chọn C: Shared Database, Shared Schema with Discriminator Column (`brand_id`)
- **Ưu điểm**:
  - Tối ưu chi phí và tài nguyên cụm CSDL tốt nhất; chỉ cần duy trì một pool kết nối MySQL duy nhất.
  - Quản lý Migration cực kỳ đơn giản qua Prisma (`prisma migrate deploy`).
  - Dễ dàng tổng hợp chỉ số thống kê vĩ mô (Macro analytics) cho nền tảng.
  - Tận dụng Composite Indexes trên MySQL: `(brand_id, priority, created_at)` để truy vấn cực nhanh theo từng thương hiệu.
- **Nhược điểm**: Phải đảm bảo 100% câu truy vấn đều chứa điều kiện lọc `brand_id`. Rủi ro rò rỉ dữ liệu xuất hiện nếu lập trình viên quên thêm điều kiện `WHERE brand_id = ...`.

---

## 3. Quyết định (Decision)

Chúng tôi quyết định chọn **Lựa chọn C: Shared Database, Shared Schema with Discriminator Column (`brand_id`) kết hợp Cơ chế Ép buộc Tenant Scope ở tầng ORM / Data Access Layer**.

### Các Biện pháp Kỹ thuật Đảm bảo An toàn Tuyệt đối:
1. **Trường khóa ngoại bắt buộc**: Mọi bảng nghiệp vụ (`Users`, `Conversations`, `Messages`, `KnowledgeBase`, `BrandTones`, `AIFeedbacks`) đều có cột `brand_id VARCHAR(36) NOT NULL` trỏ đến `Brands(id)` kèm ràng buộc `ON DELETE CASCADE`.
2. **Cơ chế Prisma Middleware / Client Extension**:
   - Tầng Data Access Layer (`src/services/db/`) thiết lập Prisma Client Extension tự động chèn điều kiện `{ where: { brandId: ctx.brandId } }` vào mọi câu lệnh `findMany`, `findFirst`, `update`, `delete`.
   - Lập trình viên không thể gọi trực tiếp câu truy vấn nếu không cung cấp ngữ cảnh `brandId` hợp lệ được trích xuất từ JWT.
3. **Chỉ mục kết hợp (Composite Indexing)**:
   - `CREATE INDEX idx_conversations_tenant_priority ON Conversations(brand_id, priority, status, last_message_at DESC);`
   - `CREATE INDEX idx_messages_tenant_conversation ON Messages(brand_id, conversation_id, sent_at ASC);`
   - `CREATE INDEX idx_kb_tenant_active ON KnowledgeBase(brand_id, is_active, category);`
4. **Kiểm tra quyền sở hữu trước khi cập nhật**: Mọi thao tác cập nhật hoặc xóa tài nguyên đều kiểm tra:
   `WHERE id = :resourceId AND brand_id = :tenantBrandId`. Nếu không khớp, trả về lỗi `404 Not Found` (thay vì 403 để tránh rò rỉ sự tồn tại của ID).

---

## 4. Hệ quả & Đánh giá (Consequences)

### Tích cực:
1. Tiết kiệm hơn 80% chi phí tài nguyên máy chủ cơ sở dữ liệu so với phương án tách database riêng.
2. Tốc độ thực thi migration đồng bộ, trơn tru cho toàn bộ hệ thống.
3. Tốc độ truy vấn hộp thư và lọc tin nhắn `URGENT` đạt dưới 25ms nhờ chỉ mục Composite Index tối ưu.

### Tiêu cực & Biện pháp giảm thiểu:
- **Nguy cơ lỗi con người quên lọc**: Được khắc phục hoàn toàn bằng Prisma Client Extension tự động tiêm `brand_id` và bộ Unit Test bắt buộc kiểm thử ranh giới Multi-tenant cho mọi API endpoint.
